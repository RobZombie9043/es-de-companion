# CLAUDE.md

Guidance for Claude Code when working in this repository. This project is a ground-up rebuild of **ES-DE Companion**, a dual-screen companion app for the ES-DE emulation frontend, using modern Android best practices.

This document is deliberately weighted toward **structure, layering, and code quality** rather than a fixed feature spec. The core state pipeline is foundational and must be built to a higher standard of rigor than everything else in the app.

## The One Thing That Has To Be Rock Solid

Everything this app does depends on correctly understanding what ES-DE is currently doing. The pipeline is:

```
es_log.txt (raw text, growing/truncating file)
    → tail new lines
    → filter for "Scripting::fireEvent():" lines
    → parse into a typed Event
    → reduce events into a single current AppState
    → AppState drives everything downstream (media lookup, UI, widgets, whatever comes later)
```

This pipeline is the foundation everything else is built on. Treat it accordingly:

- It lives entirely in `domain`, as plain Kotlin with no Android framework dependencies where at all possible — the parsing and state-reduction logic should be testable with plain unit tests against fixture log lines, with no emulator, no instrumentation, no mocked Android classes.
- It should have the best test coverage of anything in the codebase. Every event type, malformed/unexpected line, empty-args case, and the truncate-on-restart case need explicit tests.
- Resist the urge to let UI or media-resolution concerns leak into this layer. Its only job is: raw log text in, correct `AppState` out. Nothing else should influence it, and it should not know anything about widgets, screens, or file paths for media.
- If this layer has a bug, the entire app is wrong regardless of how polished anything built on top of it is. Prioritize correctness and clarity here over cleverness or premature abstraction.
- **Cold start is not "replay the last event."** A freshly-launched app has no state to reduce onto, and context-dependent events (e.g. `screensaver-end`, which needs to know what was active *before* the screensaver started) produce the wrong result if the reducer only sees the single most recent line. `EsdeLogFileRepository` instead finds the last self-contained ("anchor") event and replays forward from there, growing its read window backward until it finds one or hits the start of the file. See `EsdeLogFileRepositoryTest` for the anchor-replay cases. That replay is also skipped if `es_log.txt`'s `lastModified()` predates the current boot — a device reboot can auto-start this app (it carries a `HOME` intent filter for secondary-display placement) before ES-DE has (re)written the log this session, so an anchor found in a not-yet-touched-since-boot file is guaranteed to be a leftover from before the reboot, not current truth.
- **The derived `AppState` stream is shared, not rebuilt per subscriber.** `ObserveAppStateUseCase` computes its reducer fold exactly once, at construction, as an application-scoped `StateFlow` — not fresh on every `invoke()` call. See Known Gotchas for why a naive per-call `scan()` silently produces stale/`Idle` state for late-joining subscribers.

## Architecture & Structure

**Clean Architecture, three layers, strictly one-directional dependencies:**

```
ui        → depends on → domain
data      → depends on → domain
domain    → depends on → nothing (no Android imports, no other layers)
```

- `domain`: models, the event parser, the state reducer, use-case classes, repository *interfaces*. Pure Kotlin. This is the layer that should be easiest to read, test, and reason about — it's the specification of what the app does, independent of how.
- `data`: repository *implementations* — file I/O, log tailing, media file resolution, persistence. Talks to Android/filesystem APIs. Implements the interfaces `domain` defines, never the reverse.
- `ui`: Compose screens + ViewModels. ViewModels depend on `domain` use cases/repository interfaces only — never directly on `data` implementations, never directly on `java.io.File`, `PackageManager`, or `FileObserver`.

Keep this a **single Gradle module** with package-based layering (`domain/`, `data/`, `ui/` packages) rather than splitting into multiple Gradle modules. Multi-module setups add build-config overhead that isn't justified at this project's size; package boundaries plus code review discipline are enough to keep the dependency rule honest. Revisit this only if the codebase grows enough that build times or team size actually demand it.

**Within each layer, favor small, single-purpose classes over large ones.** A class that parses log lines should not also decide file paths. A ViewModel for one screen should not accumulate responsibilities for another. If a class is hard to name in one sentence, it's probably doing too much.

## Code Quality & Maintainability Standards

- **Immutability by default.** Data classes with `val`, not `var`. State changes happen by producing a new value, not mutating an existing one. This matters most in the state-reduction pipeline, where a mutable shared state object is the classic source of subtle bugs.
- **No `!!`.** Handle nullability explicitly at the point where it arises, not by asserting it away.
- **Explicit over implicit.** Sealed classes for anything with a closed set of variants (event types, UI state, results). Exhaustive `when` blocks with no `else` branch where the compiler can enforce completeness — this is what catches "forgot to handle the new event type" at compile time instead of runtime.
- **Errors are values where they're expected, exceptions where they're not.** Parsing a malformed log line is an expected, routine outcome — represent it as a nullable/`Result` return, not a thrown exception. A genuinely unexpected failure (e.g. can't open a file that should exist) can throw, but should be caught at a clear boundary rather than left to propagate into UI code.
- **Small, well-named functions over comments explaining what a large function does.** If a comment is needed to explain *what* a block does, that block is usually better extracted into a named function. Comments should explain *why*, not *what*.
- **Coroutines + Flow for all async work** — no callbacks, no `AsyncTask`, no `LiveData`. `StateFlow` for observable state, `SharedFlow`/`Channel` for one-off events.
- **Dependency injection, consistently applied.** Either Hilt or a hand-rolled composition root — pick one deliberately and use it everywhere; don't mix DI approaches or fall back to ad-hoc singletons partway through the codebase.
- **Testability is a design constraint, not an afterthought.** If a class is hard to unit test, that's usually a sign it's reaching across layers it shouldn't, or mixing concerns. Prefer constructor injection of dependencies (including things like a `Clock`/time source, or a `FileSystem` abstraction) so tests can substitute fakes.
- **Consistent formatting, enforced by tooling, not convention.** `ktlint`/`detekt` run as part of the build (`org.jlleitschuh.gradle.ktlint` and `io.gitlab.arturbosch.detekt`, applied in `app/build.gradle.kts`), not as a manual habit. Both are baselined (`config/ktlint/baseline.xml`, `config/detekt/baseline.xml`) against the pre-tooling codebase, so `ktlintCheck`/`detekt` only fail on *newly introduced* violations — don't regenerate a baseline to silence a violation in code you're actively touching; fix it instead. Regenerating (`ktlintGenerateBaseline`/`detektBaseline`) is only appropriate when deliberately doing a repo-wide reformat pass.

## What This Rebuild Explicitly Removes

The legacy app generated and wrote its own shell scripts into ES-DE's `scripts/` folder and had ES-DE call them on each event, producing separate companion-owned log files. **That mechanism is gone.** ES-DE already writes every event to its own `es_log.txt` via `Scripting::fireEvent()` calls — the rebuild only ever *reads* that file. No script writing, no script folder configuration, no "enable custom event scripts" setup step. Confirmed: ES-DE writes a fresh `es_log.txt` on every restart (truncated/recreated, not appended-forever), so the tailer must detect a size decrease and reset its read position rather than assuming monotonic growth.

## Feature Status

- **Log pipeline, state reduction, media resolution, onboarding, Settings, and the App Drawer are built** and described in README.md — treat their existing structure (package layout, repository interfaces, use cases) as the pattern to extend, not a sketch to redesign.
- **Widget overlay system is built** and has fully replaced the old fixed backdrop/logo
  display (`MainScreenImages`/`MainScreenImageState`, both deleted). Two canvases
  (System, Playing), grid-based placement, full CRUD edit mode (move/resize/add/remove/
  configure/reorder), DataStore persistence per canvas, and an edit-mode preview sourced
  from the last browsed system/game (`LastKnownContextRepository`) rather than the live
  `AppState`. See `ui/widgets/` (live rendering) and `ui/widgets/edit/` (the editor) —
  treat this as the pattern to extend for further widget types/config options, not a
  sketch to redesign.
- **Second-display presentation**: the app is a plain single-Activity app placed on the secondary display via the OS/Mjolnir, launching specific apps onto it via `ActivityOptions.setLaunchDisplayId` (see `SecondaryDisplayResolver`). No in-app `Presentation`/`DisplayManager` complexity beyond that.
- **In-app update checker/downloader/installer is built.** Checks GitHub Releases (`RobZombie9043/es-de-companion`) for a newer `versionName` than the running build: a silent, non-blocking check on every app start that auto-shows a dialog if an update is found, plus a manual "Check for Updates" entry as the top item of Settings → Other Settings. Confirming downloads the release APK, handles the Android 8+ `REQUEST_INSTALL_PACKAGES` grant (`InstallUnknownAppsPermission`, same shape as `AllFilesAccessPermission`), and launches the system installer via `FileProvider`. Separately, on the first startup after the app relaunches with a newer `BuildConfig.VERSION_CODE` than last recorded, a one-time "what's new" dialog fetches and shows that specific release's own notes (`GET .../releases/tags/v{VERSION_NAME}`, not "latest"). Version comparisons go through `domain/update/VersionComparator` — it compares the numeric `X.Y.Z` tuple first, then treats a no-suffix build as newer than a suffixed one at equal version, falling back to a plain string compare only when both are suffixed; this is a documented best-effort heuristic, not strict semver, given this project's irregular git tag history (`v0.6.0-pre-release`, `v0.7.0-alpha`, etc.). See `domain/update/`, `domain/repository/UpdateRepository.kt`, `data/update/`, `ui/update/`.
- **FAB Control is built.** Replaces the old fixed Settings/Music corner FABs and the "Show Settings Button" toggle with one Settings > UI Settings > "Floating Action Buttons" panel assigning a `FabType` (`Music`, `Settings`, `GameManual`, `AppDrawer`, `CustomApp`, `None`) to each of the four `FabPosition`s (`TopStart`/`TopEnd`/`BottomStart`/`BottomEnd`), persisted as `FabAssignments`/`FabSlot` (`domain/model/`). `FabAssignments.with()` is the one cross-corner business rule — `Music` can only occupy one top corner, and reassigning it there swaps the displaced `FabSlot` (including a `CustomApp`'s package selection) into the vacated corner rather than discarding it; unit-tested in `FabAssignmentsTest`. `Settings`/`AppDrawer` are rendered by `MainScreen` itself (their click handlers are local closures `MainActivity` can't reach); `Music`/`GameManual`/`CustomApp` are rendered from `MainActivity` via `MainScreen`'s four overlay slots (`fabSlotContent`, generalized from the old single `topStartOverlay` slot). `GameManualViewModel`'s manual resolution now follows `AppState.currentGameReference()` (Playing/Browsing/Screensaver-with-game) unconditionally, rather than being gated by the "Game Playing Behavior" setting — the FAB needs to know "does this game have a manual" independent of whether that automatic-display setting is even on. `CustomApp` shares the App Dock/App Drawer's `ObserveOtherScreenLaunchAppsUseCase`/`SetOtherScreenLaunchAppsUseCase` preference set and indicator dot, not a separate preference. See `domain/model/{FabType,FabPosition,FabAssignments,FabSlot}.kt`, `domain/usecase/{Observe,Set}FabAssignment*UseCase.kt`, `ui/settings/SettingsContent.kt` (`FabControlSetting`), `ui/main/MainScreen.kt`, `ui/MainActivity.kt`.
- **Backup & Restore is built.** Settings > Setup > "Backup & Restore" exports every user-configurable setting (Setup folder paths, UI/Video/Music/Other Settings toggles, `FabAssignments`, App Drawer/Dock settings and folders, and both widget canvases) to a single JSON file via a "Save As" picker (`ActivityResultContracts.CreateDocument`), and restores it back via a file picker (`ActivityResultContracts.OpenDocument`) behind a confirmation dialog — a full overwrite of everything the snapshot covers, not a partial merge. `domain/model/AppConfigBackup.kt` is the plain snapshot model (with a `version` field for the schema); `domain/repository/ConfigBackupRepository.kt` does pure `AppConfigBackup ⇄ String` serialization (implemented by `data/backup/JsonConfigBackupRepository.kt`, reusing `WidgetLayoutDto`/`WidgetLayoutMapping` for the canvas fields); `domain/usecase/{Export,Restore}ConfigBackupUseCase.kt` orchestrate the five settings repositories directly (not their narrower per-field use cases, since backup needs every field at once). `data/storage/ConfigBackupFileIo.kt` is a `SafPathResolver`-style sibling for this feature specifically: it reads/writes via `ContentResolver` open streams rather than resolving a plain filesystem path, since a "Save As" destination may be a genuine SAF/cloud document rather than local storage — called directly from `ui/settings/SettingsContent.kt`'s `BackupRestoreSetting`, never from `SettingsViewModel`. Restoring an older-schema backup is a documented additive-only convention (new `ConfigBackupDto` fields get Kotlin defaults so old backups still decode); restoring a *newer*-schema backup than the running build understands is rejected outright via an explicit `version` check, not left to silent lenient decoding. See `SettingsViewModel.restoreBackup()`/`reloadSettingsState()` for why a successful restore reloads the ViewModel's own UI state from the repositories rather than trusting it's still in sync — a bulk restore changes settings the ViewModel didn't itself mutate.
- **RetroAchievements integration is in progress (see the `cheevos` branch), landing in sequenced PRs — treat as a work in progress, not a finished feature.** Domain scaffolding (models, repository interfaces, use cases including `GameTitleMatcher`'s title-normalization logic) and credentials scaffolding (Settings > RetroAchievements, `EncryptedRetroAchievementsCredentialsRepository`) are both built; the real `RetroAchievements/api-kotlin` client is not wired in yet — `AppContainer` currently wires `StubRetroAchievementsRepository`, which fails every Connect attempt on purpose (see its kdoc), so no credential is ever persisted by it. `RetroAchievementsCredentialsRepository` is deliberately excluded from `ExportConfigBackupUseCase`/`RestoreConfigBackupUseCase` — see AppContainer's wiring comment. Remaining work (real API client, game identification, achievement UI, manual match-override correction) is tracked in the planning doc, not restated here.

## Known Gotchas (Confirmed Fixes — Don't Re-Litigate)

These cost real debugging time to track down. If you hit a symptom that matches one of these, the fix below is already applied; look for where it lives before proposing a new one.

- **`navigation-compose` predictive-back crash (b/384186542 / b/375343407).** Adding `SETTINGS` (or any similarly deep screen) as a real `NavHost` destination triggers an `IndexOutOfBoundsException` in `PredictiveBackHandler` on the versions this project uses. Fix: `SETTINGS` is *not* in `MainActivity`'s `NavHost` graph at all — it's shown/hidden via a plain `showSettings` boolean, and `SettingsScreen`'s own internal drill-down (category list → subpage → Manage Apps) is likewise plain `rememberSaveable` state with a manual `onBack` chain, not a nested `NavHost`. `EditWidgetsOverlay` follows the same pattern (`showEditWidgets` boolean, not a `NavHost` destination). See the doc comment on `SettingsCategory`. Do not reintroduce nav-compose destinations for these screens.
- **`CrossfadeAsyncImage` needs exactly one call site per role.** Multiple `when`-branch `AsyncImage`s for what is conceptually "one thing" cause Compose to dispose/remount on state-shape change, discarding `remember`ed crossfade animation state and producing a flash to the empty background. `WidgetCanvas`'s `WidgetContentView` keys each widget by its stable `id` (`key(widget.id) { ... }`) so identity survives reordering/recomposition per-widget, the same principle generalized from the original fixed-backdrop case. Note that transparent overlay-style content (the system logo, and `MediaType.Marquees`) deliberately uses a plain `AsyncImage` instead of `CrossfadeAsyncImage` — it's a transparent PNG/SVG with nothing opaque behind it, and crossfading it briefly double-exposes the outgoing and incoming images (see `WidgetContent.Image.crossfade`).
- **Directory-as-file media paths.** ES-DE can report a ROM *directory* (e.g. a `.m3u` multi-disc folder) as the launchable unit, and does not strip the trailing extension in that case the way it does for an ordinary file — the extension there is the directory's literal name, not a stripped file extension. This can't be determined from the path string alone; `GameMediaPathResolver` takes an explicit `romIsDirectory: Boolean` computed via real filesystem `File.isDirectory` checks in the data layer, keeping the resolver itself pure and unit-testable against fixture paths.
- **Hardware/system back must never exit the app.** It's meant to run continuously on a secondary display. Handling is a `BackHandler` in `MainScreen` (closes the App Drawer if open, otherwise consumes the event and does nothing), a separate `BackHandler` in `SettingsScreen` driving its own back-stack state, and a step-back `BackHandler` in `EditWidgetsOverlay` (dialog → deselect widget → exit edit mode). There is no debounce/gating layer over any of these — a suspected vendor-ROM synthetic-back-event issue turned out, on investigation, to be an unrelated third-party key-mapping app intercepting the physical button, not anything in this app's own back handling; confirmed twice now across two separate build phases. If a back-button freeze or double-fire resurfaces, check for an interfering key-mapping/accessibility app on the device *first*, then verify it isn't one of the already-fixed causes above, before adding new debounce machinery.
- **Cold `Flow`s collected independently by multiple ViewModels duplicate their upstream work.** `EsdeLogRepository.observeEvents()` is a cold `Flow` — every ViewModel that collected it independently was triggering its own `FileObserver`, its own fallback poll timer, and its own parsing of the same log lines, all running concurrently for the app's entire kiosk uptime. Fixed by `SharedEsdeLogRepository`, wrapping the tailer in `shareIn()` so there's exactly one collection regardless of subscriber count. The same lesson applies one layer up: `ObserveAppStateUseCase`'s reducer fold must also be shared (`stateIn`, not rebuilt per call) — the raw event stream beneath it has no replay, so a late-joining subscriber (e.g. a ViewModel restarting after its own `WhileSubscribed(5_000)` expires while Settings/Edit Widgets was showing) rejoined an already-warm stream with no history and sat at `AppState.Idle` until the next live event, even though the real current state was something else entirely.
- **`pointerInput` closures go stale unless the key includes everything they read - but the key must NOT include values that change mid-gesture.** A drag detector keyed only on a widget's `id` kept using that widget's *original* size/position for its bounds clamp even after a resize changed it (`pointerInput` only restarts its coroutine, and re-captures its closure, when its key changes) — a widget resized smaller than the screen became stuck unable to move, since the clamp still used its old full-screen size. Keying on the whole mutable object instead fixes staleness but breaks continuous dragging: the object changes on every cell crossing *during the same gesture*, and each key change cancels/restarts the coroutine, ending the gesture and requiring a new finger-down. Fix: keep the key narrow and stable (id + whatever's genuinely static, e.g. cell size), and use `rememberUpdatedState` to read the latest value only where it should be fresh (e.g. `onDragStart`), not as the key itself. See `EditWidgetsOverlay`'s `PlaceholderWidgetBox`/`ResizeHandle`.
- **Delta-based drag gestures can't reach a container's true edge on their own.** Growing a size/position in proportion to finger movement works until the finger nears the physical screen edge — there's no more room left to move onto, so the last cell(s) of travel can never accumulate. Fix: track the gesture's actual on-screen position separately from the per-cell accumulator, and snap straight to the boundary once that position is within a small threshold of the true edge, rather than requiring exact remaining distance. See `ResizeHandle`'s `EDGE_SNAP_THRESHOLD`.
- **System gesture-navigation edge zones intercept touch before Compose sees it.** Dragging a widget toward the screen edge in Edit Widgets lost tracking right at the boundary — Android's edge-swipe gesture zones (back-gesture areas) claim touch input in those regions regardless of what the app wants. Fix: `View.systemGestureExclusionRects`, set for the duration `EditWidgetsOverlay` is visible and cleared on exit via `DisposableEffect`, so it doesn't affect back-gesture behavior anywhere else in the app.
- **Persistent full-width overlay chrome can make content behind it permanently unreachable, not just hidden.** Edit Widgets originally floated a translucent header bar over the whole top of the screen; a widget resized/moved to sit entirely behind it became untappable — visible through the translucency, but touch couldn't reach it, with no way to select it again short of clearing saved data. Fixed architecturally rather than by clamping widget placement around the header: replaced it with a single small corner options button (⋮) that opens a menu, leaving the *entire* grid — including what used to be behind the header — genuinely free for widget placement.
- **Draw-order overlays (e.g. a grid-line guide) need an explicit `zIndex`, not just composition order.** Once individual widgets carry their own `zIndex` values (for layering), a purely-visual layer declared last in code can still end up drawn *underneath* a widget with a higher `zIndex` — composition order only wins when nothing has an explicit `zIndex` set. `EditWidgetsOverlay`'s grid-line `Canvas` uses `Modifier.zIndex(Float.MAX_VALUE)` so it always wins regardless of any widget's value.
- **`Modifier.align()` on a composable nested inside `AnimatedVisibility`'s content lambda is silently ignored.** `Box` only reads `BoxScope.align()` parent-data from its *direct* children — and inside `BoxWithConstraints { ... AnimatedVisibility(visible = ...) { SomeComposable(modifier = Modifier.align(...)) } }`, `AnimatedVisibility` (not `SomeComposable`) is that direct child. Putting `align()` on `SomeComposable`'s own modifier compiles fine (the extension resolves against the outer `BoxWithConstraintsScope` receiver, which is still in scope) but has no layout effect — the child silently falls back to the Box's default `Alignment.TopStart`. `MainActivity`'s `MusicFabContent` had exactly this bug for months without being noticed, because its *only* position was top-start, which happens to equal the default — the bug only became visible once the Music FAB became assignable to other corners (see FAB Control above) and the panel stayed pinned to the screen's left edge regardless of which corner the FAB was actually in. Fix: put `align()` (and any other Box-scoped placement modifiers) on `AnimatedVisibility`'s own `modifier` parameter, not on a composable inside its `content` lambda.
- **`ktlintCheck`/`ktlintFormat` and `detekt`'s bundled formatting rules disagree on some multi-line indentation and line-length forms.** `ktlint` (via `org.jlleitschuh.gradle.ktlint`) defaults to a 140-char line limit and prefers collapsing short single-expression function bodies onto the signature line; `detekt`'s default `MaxLineLength`/`Indentation` rules (via the bundled `detekt-formatting` plugin) use a stricter 120-char limit and sometimes expect *less* indentation for a `name =` value continuation than `ktlintFormat` itself applies — so `ktlintFormat` can "fix" a line into a form `detekt` then rejects, and vice versa, for lines in the 120–140 char band or nested `arg =\n    value` continuations. There's no single config change that reconciles this (encountered adding the update checker's `ui/update`/`data/update` files). Work around it per-line: prefer a block function body (`{ return ... }`) over a single-expression one when the collapsed form would land in the 120–140 range; hoist a multi-line `Modifier`/collection value out to its own local `val` before passing it as a named argument, rather than writing `arg =` immediately followed by a wrapped value, to sidestep the indentation mismatch entirely. Also don't blindly regenerate `config/detekt/baseline.xml`/`config/ktlint/baseline.xml` for these — baseline entries are keyed by exact (whitespace-normalized) signature/argument text, so adding a parameter to an already-baselined function changes its key and makes the *pre-existing* violation look "new"; when that happens, hand-edit just that function's baseline entry to match its new signature (confirmed via `git stash` that the old signature was genuinely already baselined) rather than running the full baseline-regenerate task.
- **A `rememberCoroutineScope()` tied to a composable that dismisses/removes itself doesn't outlive the dismissal.** Backup & Restore's restore-confirmation `AlertDialog` originally called `onDismiss()` (removing itself from composition, via the `pendingRestoreUri = null` state write that gated its `if` block) and *then* `coroutineScope.launch { ... the actual restore work ... }`, both using a `coroutineScope` obtained from `rememberCoroutineScope()` inside the dialog composable itself. `launch` doesn't run its body synchronously — it schedules the coroutine, and the pending recomposition that tears the dialog out of composition (cancelling that exact scope) reliably wins the race, so the restore silently never ran: no crash, no error, nothing. Confirmed on-device (export worked, restore didn't) before being traced to this. Fix: do the actual work on a `coroutineScope` that belongs to a composable which stays in composition (the dialog's *caller*, not the dialog), and make the dialog itself a dumb confirm/cancel prompt with no coroutine logic of its own — see `SettingsContent.kt`'s `BackupRestoreSetting`/`RestoreBackupConfirmationDialog`. The general lesson: never launch on a scope owned by the same composable an `onClick` handler is about to conditionally remove from composition.

## What NOT to Do

- Don't let the event-parsing/state-reduction layer depend on anything outside plain Kotlin — no Android imports, no leaking UI or media concerns into it.
- Don't reintroduce script generation/writing to ES-DE's `scripts/` folder.
- Don't bypass the repository layer to touch the filesystem or `PackageManager` from UI code.
- Don't add a general network/backend layer. The one sanctioned exception is the update checker (`domain/repository/UpdateRepository.kt` / `data/update/GitHubUpdateRepository.kt`), which talks to the GitHub Releases API using plain `HttpURLConnection` + `kotlinx.serialization` — not OkHttp/Retrofit/org.json, and not a general-purpose API/backend layer. Don't extend that carve-out into networking for anything else.
- Don't split into multiple Gradle modules preemptively — package-based layering is sufficient at this size.
- Don't add `NavHost` destinations for `SETTINGS`, `EDIT WIDGETS`, or other deep screens — see Known Gotchas.
- Don't add back-press debounce/gating logic to work around a suspected double-fire without first checking for an interfering key-mapping/accessibility app on the device, then confirming it isn't caused by one of the already-fixed issues above.
- Don't let multiple ViewModels each independently collect a cold `Flow` that does real work (`FileObserver`, polling, file reads, a reducer fold) — share it (`shareIn`/`stateIn`) at the `AppContainer` level instead. See Known Gotchas.
